# BB Rooms

BB Rooms adds shared conversations to BB's existing application. Chris clarified on October 10, 2026 that the goal is all of BB's functionality with room support inside BB. The initial separate `apps/rooms` preview proved participation and execution behavior but did not fulfill that product requirement. The native candidate now uses BB's actual frontend; complete integration of room persistence, packaging and server lifecycle remains required. Reusing BB's SDK underneath a separate chat application is insufficient.

A person opens a room in BB, invites teammates, adds independently acting agents and addresses any combination of them with `@`. BB's normal navigation, projects, sections, environments, threads, files, terminals, diffs, tools, plugins and provider controls remain available to authorized users. Rooms and ordinary agent threads coexist. Each participant sees who actually spoke, what is pending and whether work is active, waiting or idle. Agents can contribute, ask each other for help, receive human input while working and decide that nothing more needs saying.

Use BB's existing vocabulary: a project supplies work context, an environment supplies execution and workspace, a thread is an agent's persistent working conversation, and a section organizes navigation. A room adds a shared conversation and participant membership. Workshop is a room name. The preview's fixed Work Together heading is not a section model and introduces no separate organization or workspace hierarchy. Native room creation must remain discoverable in wide and compact layouts.

The shared room is not a transcript of one agent pretending to be a team. Every participant has a stable authenticated identity. Each agent has its own private execution context and deliberately publishes through a room tool or CLI. BB manages the agent's project, environment, persistent top-level thread, provider session, tools and execution lifecycle. Rooms operates those threads through BB's SDK; it does not create a separate runner or call model providers directly. Generated private text, tool output and model reasoning stay outside the public conversation. No agent can publish as another participant by changing a name in its response.

Humans and agents share the conversation model; their operational permissions differ. A room member can read public messages without being forced to answer every one. Every completed public human or agent message reaches the other room agents as optional context. Structured addressing asks particular participants for a response; it does not prevent the others from following the conversation. Each agent decides whether to publish through the room tool and may finish an evaluation without posting. Self-authored messages, unfinished streams, private output and silent completion do not start new evaluations. Conversations can continue beyond an arbitrary number of handoffs and become idle naturally. Visible resource controls and Stop/Pause keep the user in charge.

Selected public responses stream into stable message bubbles after the agent explicitly chooses to publish. Pending work is visible before the first public text. Private execution activity has a separate inspector and audience policy. Reconnect preserves messages and status; retries do not duplicate posts; cancellation and revocation prevent obsolete work from publishing later.

Success means two independently signed-in humans and two independent real agents can collaborate end to end in the hosted candidate: genuine separate replies, useful peer requests, live human follow-ups, explicit publication, meaningful silence, public streaming and recovery under failure. A demo with two generated reply bubbles is insufficient.

Room membership and permission to inspect or operate an agent are explicit. Integrating into BB must preserve its full owner experience while limiting collaborators to the resources they are authorized to use. Reuse the actual BB feature paths; embedding the standalone preview does not establish native integration.

The user has authorized replacing the current preview. Development and verification run in disposable staging; preserve Chris's current room history and stable BB/Buzz installations.
