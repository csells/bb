# Rooms inside BB

Status: native UI hosted and two-human/Codex/Claude end-to-end acceptance passed, October 10, 2026. Exact hosted fixture cleanup and actual iOS room/section creation, drawers and Send-button persistence checks also passed. Full native lifecycle integration remains open. This plan supersedes the standalone preview as the product destination; earlier participation and recovery evidence remains useful.

Chris wants BB with rooms added, retaining its existing functionality. The earlier preview ran a separate chat app using native BB threads through the SDK. It omitted BB's application shell and exposed only a small subset of its controls. The hosted candidate now serves the actual BB frontend, with visible New room and section controls in wide and compact layouts. Its separate backend lifecycle remains unfinished. See the [corrected vision](../vision/rooms.md).

## Spikes before implementation

1. **Native navigation and resources.** Trace BB's application shell, sidebar, sections, split panes, project/environment selection and thread routes. Add a disposable native room view and verify that an owner can create/open a room, organize it with ordinary threads, and open a participant's actual thread, files, terminal and diff. Exercise compact creation too. Decide how room/project associations and participant environments compose without creating an unrelated project per participant by default. Completion requires rendered evidence through BB's normal feature paths.
2. **Multiple human identities and access.** Trace trusted human identity through BB's server APIs, subscriptions, tools and workspace operations. Prove two independently authenticated humans can use the native room view, attribution cannot be forged, revocation takes effect on live connections, and membership does not grant unrelated operator access. Document which existing BB capabilities each role receives and enforce those permissions on the server. Completion requires positive and negative checks with actual server state; a route embedded in the shell alone does not pass.
3. **Persistent agent integration.** Bind independent room agents to BB-managed threads/environments and expose their existing permissions, provider configuration and lifecycle controls through BB. Reuse the explicit publication, optional deliveries, streaming commit, native steering and recovery work. Prove private outputs remain private and a participant can speak or stay silent without transcript mirroring. Qualify authentication storage/renewal separately from immediate model access.
4. **Migration and acceptance.** Preserve current humans, room history, participant identities and native thread bindings. Run two humans plus real Codex and Claude through BB's actual UI: room/section creation, context selection, dialogue, streaming, steering, silence, interruptions and recovery. Exercise representative existing BB workflows alongside rooms and record remaining coverage. Present a disposable hosted build of the full BB application. Stable promotion still requires approval of that candidate.

Each spike must leave evidence under `specs/research/spikes/` and distinguish proposed behavior, implemented behavior and verified behavior. Source/build/test/runtime work remains in disposable staging. The broad acceptance criterion is full BB capability available through its existing surfaces to authorized users, with shared room participation added; duplicating a few controls in a separate chat app does not meet it.

## Decisions and qualification

- Serve the actual BB frontend through an authenticated edge. BB's existing core APIs trust transport access; room membership cannot be treated as global operator permission. Explicit existing user IDs receive full BB access. See [access research](../research/spikes/native-rooms/access.md).
- Keep existing Rooms persistence and execution bindings. Add nullable project/environment/section associations, and preserve migrated agents' actual thread identities. New agents use the selected context. Existing-thread attachment does not rewrite workspace instructions or provider settings. See [binding research](../research/spikes/native-rooms/bindings.md).
- Native UI uses BB navigation, shared controls and real thread routes. Guests use the same room view without initializing operator queries or sockets. The initial 56 focused UI tests passed. Subsequent UI changes passed the combined 45-test app run, eight sidebar tests and the final mobile drawer regression checks. See [UI evidence](../research/spikes/native-bb-rooms/ui/README.md).
- Initial transport tests passed real HTTP/WebSocket framing, identity attribution, membership removal and live session revocation. Their upstream echo fixture verifies transport boundaries; it does not qualify actual BB terminals or tools.
- Existing recovery assumed a project was private to one agent. Shared projects require exact activation matching. A new conditional Stop must carry the expected turn through the native server, daemon and runtime so delayed cancellation cannot interrupt a successor turn. Focused regressions and an actual restarted-runtime retest prove that stale/queued stops preserve unrelated work and a current stop returns its thread to idle.
- Build and test in `/Users/admin/code/Forks/get-bb/bb-native-rooms`, with fresh data under `/Users/admin/rooms-native-qa`, inside the existing task-owned disposable VM. The verified candidate replaced the serving preview after migration rehearsal; original user data and agent bindings were preserved. Independent QA uses separate data and ports. The registry is authoritative for current ports, addresses and service lifetime.

These acceptance paths now pass: native wide/compact creation and section placement, two separate human accounts, operator and guest capability checks, representative BB workspace controls, existing-thread attachment, real Codex/Claude public dialogue and streaming, silence/quiescence, scoped Stop/recovery, restart and preserved Workshop history. See the [qualification report](../research/spikes/native-rooms/README.md). Provider access passed; unattended credential renewal remains separate and unverified. The remaining native lifecycle work is described below.

## Native lifecycle still open

The hosted candidate meets the shared-conversation and representative native workspace paths. It does not yet meet the broader all-BB lifecycle requirement: room state and dispatcher startup remain a separate service. Normal export and server move are explicitly refused at core while this mode is enabled, rather than producing an incomplete combined operation. Stock packaging/import and generic remote-agent BB CLI authority also need integration. The [lifecycle review](../research/spikes/native-rooms/lifecycle-integration.md) specifies the shared database, owned startup/freeze/recovery, package, migration and verification work. These are unmet requirements, not withdrawn scope. Durable Nova authorization remains separately pending user input.
