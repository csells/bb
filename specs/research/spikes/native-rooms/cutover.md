# Native preview cutover

October 10, 2026. The task-owned disposable VM now serves the actual BB frontend at the existing preview URL. Stable BB and Buzz were not modified.

The preview was idle before cutover: every existing BB thread was idle and no room delivery was queued, dispatching, running or uncertain. The two preview LaunchAgents were stopped. SQLite's online backup API copied the Rooms and BB databases into a private rollback directory alongside the original service plists and local-helper configuration. The directory is `/Users/admin/rooms-native-qa/preview-cutover-20261010T190150Z`; it contains credentials and is deliberately excluded from this repository.

The new core uses `/Users/admin/code/Forks/get-bb/bb-native-rooms` with the original BB data, ports and enrolled host. `BB_ROOMS_SEPARATE_SERVICE=true` prevents incomplete export and move operations at the core API. The gateway uses the actual `apps/app/dist` build, preserves the original Rooms data, grants native operator access explicitly to the existing Chris account, and uses the public HTTPS origin for agent participation commands. BB's direct machine-access URL also points to that origin. Exact origins were added only to the disposable VM helper configuration.

The migration ran before the gateway and dispatcher restarted. The first read-only comparison hit a test-helper issue: macOS system SQLite could not open the closed WAL-mode backup files without sidecars. The comparator now requires that a backup has no nonempty WAL and opens that immutable snapshot read-only; live databases still use ordinary read-only connections. The same backup then passed the complete [preservation comparison](evidence/cutover-preservation.json): all existing rows across 13 Rooms tables, both native agent bindings, provider options, project/environment context and thread history were preserved. No old turn was replayed.

Only after that comparison did the gateway reopen. The [actual core guard check](evidence/hosted-core-guard.json) verified all three lifecycle refusals. The [hosted dialogue](evidence/hosted-dialogue/evidence.json) then used the original owner's login, a separate invited human, and two real BB-managed providers in an isolated test project/room. Both agents independently published and streamed through HTTPS, both human browsers observed partial states, an undirected question reached both agents, and the closing message produced silent completions. Both browsers reloaded persisted history without a page error.

Rollback must stop both preview services and reconcile any activity after cutover before restoring a snapshot. The initial backups are not permission to overwrite newer room or thread history. The old checkout and private service backups remain available in this disposable VM; no production promotion occurred. Current addresses, supervision, expiry and teardown instructions are in registry record `bb-rooms-stage`.

This is native UI and execution integration with a separate Rooms service. Combined export/restore, stock package installation and server migration remain unfinished; see the [lifecycle review](lifecycle-integration.md). Current Claude access passed real turns, but the independent long-lived authorization timed out without user input and no token was created. That remaining authentication step is separate from the successful cutover.
