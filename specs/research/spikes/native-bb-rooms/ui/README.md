# Native room navigation and authentication boundary

The owner experience reuses BB's actual `App`, `AppLayout`, sidebar navigation model, plugin thread list, `AppPageHeader`, shared Markdown renderer and persistent responsive drawers. `/rooms` and `/rooms/:roomId` are native React routes. Room participants link to their actual BB thread through `getThreadRoutePath`; no iframe or recreated thread inspector is involved.

Room creation remains in the view header on compact and wide screens. Project, environment and section selection call BB's existing SDK. Creating a section calls the same `threadSections.create` operation as BB, and adding an agent can create an independent thread in room context or attach an existing thread. Operators receive the full BB application; room guests receive the native shared conversation component without mounting BB's global project/plugin/WebSocket bootstrap.

A session gate probes `/api/v1/rooms/session` before mounting the application. The versioned prefix matters: BB returns an explicit API 404 there on a plain installation, while unknown unversioned GET paths can return the SPA HTML. Native anonymous or guest sessions cannot start the operator application. Any account or operator-role change clears cached queries and disconnects the native WebSocket before accepting the new identity. Keyed guest/operator subtrees reset local history and drafts. Revocation or failed verification unmounts the authenticated application. The server remains the authorization boundary.

Public room history follows the existing protocol. SSE snapshots show explicit public streaming. Access errors clear the displayed room and close its stream; fallback polling only runs when SSE is not live. Failure cards remain immediately after the message that caused them. Guests cannot inspect private threads or start/attach/steer/stop native execution. Room ownership and BB operator access are independent.

## Evidence so far

`typecheck.log` records the first complete app typecheck. `tests.log` records 56 passing focused tests, including six session-boundary checks plus existing rail, sidebar, route and navigation-preference coverage. `nav-red.log` records a real regression: the initial Rooms navigation change also closed the resource sidebar when selecting Plugins or Skills. The repair limits that callback to Rooms and preserves the old behavior.

The candidate was subsequently built and typechecked by the coordinating agent before browser qualification. `browser-green-3/result.json` and its inspected screenshots establish native BB room/section creation, invitation acceptance by a separate human account, live messages with distinct authors, reload persistence, and absence of private BB API bootstrap for anonymous/guest users. Both wide and 390×844 Chromium views were exercised; settled drawer geometry was checked before screenshots, and the app root stayed enabled and visible to accessibility APIs. Room rows appeared under the newly created native sidebar sections.

`browser-red-1` records a harness selector failure: an implicit select label includes its option text, so exact `getByLabel("Project")` did not match. The rendered form was correct; semantic combobox selectors fixed the probe. The first rendered login also exposed ordinary BB onboarding; its visible Skip setup action worked. This writes `generalSettings.onboardingCompletedAt` and `setupChecklistVisible` through the existing SDK, rather than a browser-only dismissal. Three subsequent independent browser profiles opened Rooms without onboarding.

`resources-1/02-terminal.png` shows the actual participant BB thread and a zsh terminal returning `native-room-terminal-ok` through the authenticated gateway. `resources-2` verifies the final built candidate: the native README preview, a real terminal-created README change rendered as +2/-0 in BB's diff panel, built-in plugin catalog and detail content, and native General settings. The marker was removed through the native terminal, the diff returned to **No changes**, and the terminal tab was closed. All screenshots were inspected. The resource browser recorded no page errors and was closed.

`webkit-final` preserves a useful failing run. All room assertions passed, but three WebKit page errors identified a real deployment omission: the local host helper rejected the new gateway origin with HTTP 403. Registering `http://127.0.0.1:38910` in the task VM helper's `BB_DATA_DIR/client.json` changed `/status` to HTTP 200 with that exact `Access-Control-Allow-Origin`, without changing product source or restarting the daemon. Existing configuration was preserved; stable installation configuration was untouched.

`webkit-configured/result.json` is the clean final Playwright WebKit run against the built candidate, with no page errors. It covers anonymous and guest API isolation, native project and section creation, an invitation and two distinct human identities, live delivery and reload persistence, compact drawer geometry and app-root accessibility, and cleared name/project fields when reopening the creation form after success. The wide and compact screenshots were inspected. Every owned browser exited. This engine is Playwright WebKit, not actual iOS Simulator Safari; the separate iOS qualification records that evidence.
