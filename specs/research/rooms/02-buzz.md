# Buzz gives agents an explicit voice

Buzz's important architectural choice is that **the agent decides when to publish**. A relay event reaches an ACP harness, which prompts an independently identified agent. The agent operates privately and invokes the Buzz CLI to send a message. Provider completion is not automatically converted into a public reply. Each named agent receives a distinct Nostr keypair; multiple execution workers under one harness still share one bot identity. ([Architecture and identity](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/README.md#L7-L47))

## Publication carries identity, recipients and a receipt

`buzz messages send --channel UUID --reply-to EVENT_ID --mention RECIPIENT_KEY --content -` reads selected text from stdin. The CLI validates recipients against channel membership, derives thread metadata, builds an event, signs with the executing agent's key and submits it. The success result includes the actual signed recipient keys. A generated name in a paragraph is not another agent's authenticated participation. ([Message implementation](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-cli/src/commands/messages.rs#L601-L757), [identity-bound signing](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-cli/src/client.rs#L580-L607))

Buzz's prompt distinguishes useful publication from reflexive chatter. Human requests require an answer; useful results are published; otherwise silence is usually correct. It prohibits bare acknowledgments and mentions used only as narrative decoration. Completed delegated work mentions the delegator, while accepting an assignment does not. Code separately suppresses self-authored events. **These rules reduce loops without imposing a fixed conversation length**, although they cannot prove deliberate mutual mentions will always terminate. ([Participation rules](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/base_prompt.md#L43-L80), [self suppression](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/lib.rs#L3563-L3566))

## Scheduling is independent from the message log

Buzz maintains scoped queues, active sessions, retry state and withheld steering events. Session context defaults to per-channel, with per-thread scope available. The same named agent can have several sessions that share files and durable memory without sharing provider context. Admission policy additionally controls which authors can wake the agent; the documented default is owner-only. A room with two humans is not functional merely because both can see an agent's name. Both must be admitted to request its work. ([Queue](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/queue.rs#L368-L460), [session contract](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/session_model_thread.md#L1-L5), [author gate](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/README.md#L134-L187))

Busy inputs can queue, steer or interrupt. Steering uses an adapter-advertised capability and checks recognized delivery outcomes; a generic successful JSON-RPC `{}` is not enough. Unsupported adapters fall back to cancellation plus merged input. This protects accepted human messages from disappearing when a provider does not implement live steering. ([Capability and fallback](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/acp.rs#L1490-L1560), [acknowledgment](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/acp.rs#L1670-L1728))

Publication retries reuse identical signed event bytes; ambiguous exhausted retries return an unknown-delivery result instead of inviting a new duplicate write. Relay event IDs provide deduplication, while incoming replay uses bounded remembered IDs and timestamps. This is useful engineering, not a guarantee of exactly-once agent execution under arbitrary failure. ([Publication retry](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-cli/src/client.rs#L1120-L1172), [bounded replay deduplication](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/relay.rs#L1094-L1103))

## Public streaming and private activity are different features

Buzz streams ACP activity separately. Its observer encrypts telemetry to the owner and publishes a dedicated frame; ordinary room message publication remains the explicit CLI path. The browser renders incremental activity, but that does not establish selected public reply token streaming. Forwarding these owner-only frames into a room would change their audience and violate the separation we need. ([Owner telemetry](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/lib.rs#L1791-L1830), [activity renderer](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/src/features/agents/activity-transcript.ts#L431-L450))

The inspected Buzz web broker also loads **one key and one viewer for all browser clients**. It is a personal browser host, not independent multi-human authentication at one URL. Reuse the relay/participation design, but do not confuse that broker with the desired shared web product. ([Browser identity](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/browser-host/relay-broker.mjs#L698-L716))
