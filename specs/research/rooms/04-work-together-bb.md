# Work Together separates execution from reporting

The initial Work Together audit was inadequate for designing a peer chat room. It identified a BB execution cell and separate web/MCP/worker services, but did not trace a complete public-message lifecycle. The implementation then reused independent threads while missing the strongest lesson available in the source: **agents report deliberately through trusted tools**. Work Together remains useful evidence for execution admission and tool authority, not proof of an arbitrary multi-agent chat service whose companion code was unavailable. ([Original audit](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/specs/research/work-together.md), [execution-cell scope](https://github.com/timmoshu/bb/blob/0f53aacbec1a46680e6aa392408ad7f8d1333c87/docs/bb-candidate-cell-release.md#L1-L10))

## Reports use trusted execution identity

`wt_checkpoint_report`, `wt_result_report` and `wt_needs_you_report` accept structured reports and idempotency keys. The model cannot choose actor, goal, workspace or thread identity in those arguments. The handler injects trusted `bbThreadId` and server-held authorization. Result reporting does not automatically finish work; the needs-you tool explicitly directs the agent to report once and stop. These are work-state tools, not general room-post APIs, but their authority boundary is directly relevant. ([Contracts](https://github.com/timmoshu/bb/blob/0f53aacbec1a46680e6aa392408ad7f8d1333c87/apps/server/src/services/work-together-settlement-tools.ts#L7-L160), [trusted injection](https://github.com/timmoshu/bb/blob/0f53aacbec1a46680e6aa392408ad7f8d1333c87/apps/server/src/services/work-together-settlement-tools.ts#L170-L238))

The room-distribution adapter at `848ad9550784c5ff22ea962aa5d757c3f1d91084` exposes binding-scoped bootstrap, commands, events and subscriptions. Its stream target selects a primary thread or child attachment; it is not itself a peer social message bus. It provides exact-turn steering/interruption, queue-if-active sends, authenticated actor stamps and replay/conflict handling. `branch.publish` publishes repository branches, not chat messages. ([Adapter port](https://github.com/timmoshu/bb/blob/848ad9550784c5ff22ea962aa5d757c3f1d91084/apps/server/src/room-distribution/room-distribution-port.ts#L10-L58), [commands](https://github.com/timmoshu/bb/blob/848ad9550784c5ff22ea962aa5d757c3f1d91084/apps/server/src/room-distribution/binding-backed-room-commands.ts#L730-L819))

## Referenced PRs do not establish upstream room support

Upstream PR2324 was a Grok launch-options change opened against the wrong repository and closed unmerged; its author pointed to downstream PR7. It was not an upstream BB Rooms implementation. BB multiplayer PR799 was also closed unmerged and explicitly described claimed identities rather than identity-based authorization. These facts do not rule out other work, but they prevent citing either PR as proof that the needed product already exists. ([PR2324](https://github.com/get-bb/bb/pull/2324), [author correction](https://github.com/get-bb/bb/pull/2324#issuecomment-5389393496), [downstream PR7](https://github.com/timmoshu/bb/pull/7), [PR799](https://github.com/get-bb/bb/pull/799))

## BB supplies the execution substrate, not the social protocol

BB's plugin SDK registers schema-validated tools and selects tools/instructions per session. The native tool context includes trusted thread and project IDs plus cancellation. Pi's actual bridge registers those tools and routes invocations. That is a plausible implementation path for Rooms publication rather than depending on shell prose parsing. ([Tool registration](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/packages/plugin-sdk/src/backend-contract.ts#L1615-L1668), [Pi bridge](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/plugins/provider-pi/src/bridge/bb-pi-extension.ts#L311-L343))

There is a critical missing piece: the inspected tool context has **no trusted immutable run/turn ID**, and mutable configuration metadata is explicitly untrusted. A thread binding can identify an agent, but stale work needs a revocable activation lease or an added trusted run context before it can safely publish after interruption. The replacement must prove that fence, not pass a model-supplied turn ID and call it authentication. ([Context](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/packages/plugin-sdk/src/backend-contract.ts#L1068-L1082), [metadata trust warning](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/packages/plugin-sdk/src/backend-contract.ts#L1141-L1155))

Work Together companion MCP/web/worker source was not found among the inspected public repositories. Its unpublished scheduler and chat semantics remain unknown. No Work Together deployment or suite was run for this audit.
