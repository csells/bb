# Transcript mirroring created the wrong boundary

The preview has real independent agent threads, but **its public conversation is a projection of provider transcripts**. Builder's embedded Reviewer paragraphs are therefore text generated inside Builder's response, not independently authenticated Reviewer messages. The source permits this because it copies every assistant conversation row into the room under the executing agent's identity. A better role prompt cannot make that projection a correct participation protocol. ([Audited runtime](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L165-L225))

## Independent execution does not establish independent speech

The runtime creates a project/workspace and persistent BB thread for each agent, with no parent thread argument. That execution separation is useful and should survive replacement. However, the room API authenticates human bearer sessions, while public agent attribution comes from transcript mirroring. Agents cannot authenticate to a room-specific publication command as themselves. The required correction is an authenticated publication boundary, not replacing two real threads with another orchestration prompt. ([Thread creation](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L86-L155), [human message route](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/app.ts#L249-L269))

Each activation receives a snapshot of up to 80 complete non-tool messages, bounded to 32,000 characters and 12,000 per message, plus a textual `[[ask @handle: request]]` convention. There is no agent inbox, consumption cursor, publication receipt or room-read tool. Still-streaming peer messages are excluded. This can encourage a model to continue the supplied transcript, but the exact model-internal reason for the user's screenshot is unproven. The demonstrated defect is simpler: any simulated voices that appear in provider text are automatically public. ([Prompt construction](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L100-L121))

## The two-handoff cap is hidden causal-depth truncation

The cap was introduced by this prototype, not required by BB. Human messages have depth zero. Each mirrored agent message increments the triggering message's depth. After the agent finishes, the adapter scans only its final assistant row for exact whole-line handoff directives and processes them only when the triggering message's depth is below two. At the boundary it silently ignores further directives. ([Depth and parser](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L185-L261))

For one chain this permits human → Builder → Reviewer → Builder, then drops another handoff. It is **not a global two-transfer budget**: multiple addressed agents and multiple recipients can fan out into more calls. The prompt describes a broader limit than the code implements. The replacement must remove this hidden semantic restriction and use intentional addressing, natural no-post completion and explicit operational controls that report when they pause work. ([Prompt wording](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L121))

## Preserve infrastructure and replace the conversation contract

Room persistence, membership checks, independent workspaces and provider threads are foundations. Transcript publication, regex handoffs, implicit agent identity and depth-based suppression are not. The new implementation should keep provider events in private execution history and expose public messages only after a participant's explicit authenticated tool call. Acceptance must test that a provider can finish with substantial private output and **zero public messages**. The rest of this report specifies that replacement rather than treating the current demo as a nearly complete multi-agent room.
