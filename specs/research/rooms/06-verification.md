# Verify boundaries before declaring rooms ready

Research establishes why explicit participation is necessary; it does not prove our new implementation works. The existing hosted preview's successful two-human/two-model tests are historical evidence of connectivity, membership and execution. They do not establish authenticated agent publication, successful silence, durable peer delivery or selected public streaming. Replacement acceptance must target those missing semantics rather than count reply bubbles.

## Executed reference fixtures validate specific mechanisms

Gas City reference tests completed in `/Users/admin/gascity-participation-spike` inside the disposable Rooms VM. **46 top-level Go tests passed with `-race` (55 passing events including subtests), and 88 Python tests passed.** They exercise pinned upstream code with fake Slack/GC endpoints, including routing, receipts, immutable turn references, fanout and recovery. They do not prove live Slack credentials, live model compliance, or our BB integration. [Commands, machine-readable result and logs](../spikes/gascity-reference/README.md).

Buzz and Work Together conclusions come from pinned source inspection. Their tests were read, not rerun against those services. No stable BB or Buzz runtime was changed by this research. Source limitations are retained in the chapters: Buzz's personal browser identity, owner-only activity streaming, bounded replay; Gas City's one-hop formal delegation and ordinary-reply durability gap; unavailable Work Together companion behavior.

## The controlled protocol spike completed

A scratch broker and CLI were exercised under `specs/research/spikes/explicit-participation`, in `/Users/admin/rooms-participation-spike` in the disposable VM. The source implements immutable actor/room/activation capabilities, explicit post/request, public stream lifecycle, acknowledgment and settlement with SQLite persistence. **12 deterministic protocol assertions passed**, including conflicting stream-commit recipient retries returning 409, immutable two-room capabilities and cancellation fencing surviving broker restart. A controlled real two-agent BB/Pi fixture passed **11 assertions**: separate A/B CLI posts, private simulated dialogue and raw mentions remaining unpublished, explicit begin/append/commit producing one message, chunks causing no wake, and no-post completion returning idle. These results exercise exact commanded tool sequences, not autonomous social-policy selection. The first two live attempts failed through a model refusal and malformed JSON/command ordering. The busy-tool test also passed: a second human message was durably accepted while AgentA ran a real sleep tool, BB returned a queued receipt, and AgentA later observed it. This proves native busy queueing, not active-turn steering. The scratch broker still records that delivery queued because the fixture does not implement automatic queue-to-provider reconciliation. The latest detailed checkpoint is [the spike handoff](../spikes/explicit-participation/HANDOFF.md).

The essential negative test is that an agent can emit a fake multi-speaker transcript privately and create zero public messages. Positive tests must prove each real agent posts under its own credential, one targeted post wakes only its intended peer, no-post completion reaches idle, and a useful conversation can exceed two exchanges. Two humans must submit while agents are active without identity loss or dropped input. Streams must reconnect into the same public message without waking peers per chunk. Lost acknowledgments, restart, cancellation and revocation must not allow duplicate posts or stale publishers.

## Remaining uncertainty must be explicit

Model-authored public streaming is now established separately for actual authenticated Codex and Claude providers, after explicit user approval for private credential transfer to the disposable VM. Generic begin/append fixtures alone could not establish that result. The implemented CLI binds each activation to an immutable capability; real SQLite and actual-provider tests cover leases, membership, notification intent and stale-publication rejection. The scratch broker alone does not prove those candidate behaviors. An independent review found a conflicting commit retry that changed recipients; it was fixed to return 409 and tested. Same-UID processes sharing a filesystem are not strong credential isolation; the preview remains intended for trusted collaborators. Selected text is published across explicit model-authored append calls, with tool-round-trip latency; private provider tokens are never automatically forwarded. The final hosted artifact also passed twelve mixed-provider conversation/control groups and separate natural Codex and Claude stream cases in two signup-authenticated human browsers, as detailed below.

The user authorized replacement of the preview and requested necessary spikes. Candidate implementation therefore proceeds without another conceptual approval gate. Promotion into the stable BB installation remains a separate action under the global isolation rules. ## Actual transport faults preserve accepted human work

A fault proxy around the **actual BB core** reproduced a lost-steering-acknowledgment defect: the original native execution completed and the old gateway released its activation before the delayed input's outcome was known. The fix persists an immutable steering ID, exact input text and activation/thread binding before dispatch. Only exact native terminal admission proof or a successful atomic queue-cancellation receipt settles that record. Known in-flight sends retain their lease; lost acknowledgments and crash-orphaned submissions remain fenced without replay.

Four actual Codex/BB fault scenarios passed: lost ACK before admission (**7 checks**), gateway SIGKILL before admission (**7**), lost ACK after real admission (**6**), and delayed successful ACK (**5**). They verify premature recovery is rejected, late exact proof enables recovery, independently queued human requests survive and later execute, private output remains unpublished, and a legitimate delayed successful send is not falsely fenced. Only the gateway-crash case actually restarts the gateway; the evidence report corrects older generic assertion labels that mentioned restart in the other cases.

The first repaired fault run exposed a second bug: owner recovery canceled unrelated never-dispatched room follow-ups. Recovery now fences active execution while preserving those queued requests. A further actual-BB red/green regression caught the same broad cancellation when native execution was interrupted externally; the corrected path passed **5 checks** proving the queued human request survives and executes while only the old activation stops. Explicit **Rooms Stop** remains the deliberate action that cancels active and queued room work. Real database tests separately cover restart persistence, exact binding, atomic cancellation and delayed-error guards. [Fault evidence and final 26-test build](../spikes/explicit-participation/runtime-v2/README.md).

The final mixed Codex/Claude hosted artifact passed **twelve conversation/control groups**, plus separate naturally authored stream cases for **each provider**. Both signup-authenticated human browsers saw each message grow through at least three distinct in-progress text states and finish under the same ID. The mixed run found and drove a fix for budget drafts being reset by delayed snapshots. Later observer instrumentation and an approval-wait timeout affected test capture, not publication correctness; those failures remain preserved. A real owner Allow once action approved a reviewed room-publication command through the UI, and the focused Claude retry retained both original browser observers. This is separate-run evidence, not one uninterrupted fourteen-group success. See the [candidate verification report](../../validation/rooms-v2/README.md). No stable installation has been promoted.
