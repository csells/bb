# BB and Work Together: explicit participation audit

## Why does Rooms manufacture a conversation inside one agent response?

### Takeaway
The implementation creates real independent BB threads, but publishes their entire assistant transcript as chat. It lacks an agent-authenticated publication API/tool. The embedded voices are text generated by one model, not separate authenticated posts; attribution at the bubble boundary does not make that prose a real conversation.

### Cited Findings
- Current pinned staging is `a05bc0eea5ede0ffe2a99cf607c55e1afef43e34`. Each agent gets its own project/workspace and persistent BB thread; spawn has no parent argument. Existing threads receive another prompt. — [Runtime](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L86-L155)
- Every assistant conversation row after a baseline is directly upserted into the shared room under the current agent's ID, without any explicit publication decision. Nested rows are requested. Tools are also copied into room messages. — [Runtime](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L165-L225)
- The prompt encourages collaboration through a textual `[[ask @handle: request]]` convention, after including the latest 80 complete, non-tool messages under a 32,000-character budget, truncated to 12,000 characters per message. There is no agent inbox, unread cursor, receipt, or room-read tool in this adapter. Other agents' still-streaming replies are excluded. — [Prompt construction](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L100-L121)
- Existing rooms SDK/CLI uses human session bearer credentials. POST messages calls `requestMessage(user,...)`, which unconditionally assigns kind human and server-derived user ID. Agent identity currently comes only from the transcript mirror, not authenticated agent API calls. — [API](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/app.ts#L96-L118), [message route](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/app.ts#L249-L269), [store](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/store.ts#L307-L331)
- Normal messages to busy agents enter the Rooms queue; the runtime refuses to start another delivery while one is non-queued. Steer is a separate call into BB `mode: steer`, with the human message persisted before provider submission and no immutable expected turn ID. — [queue](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L72-L83), [steer](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/app.ts#L280-L291)

### Inferences
- The screenshot's blended voices are consistent with a small model simulating both speakers in its own completion, then the adapter publishing that completion verbatim. We cannot prove model-internal cause, and must not claim the reviewer actually produced the embedded reviewer paragraphs.
- Context repeated as a JSON transcript, together with discussion instructions, encourages transcript continuation; better prompts alone cannot establish publication authority or independent participation.
- Equal social participants need a shared authenticated message protocol and independent private execution loops. Top-level independent sessions already exist; the missing boundary is explicit publication and durable delivery.

### Gaps
- This source inspection did not replay the exact user's request or inspect their private full transcript. The structural defect is sufficient to explain why simulated voices would become visible, without doing so.

## What does the two-handoff cap really do?

### Takeaway
It is an invented per-causal-path depth limit, not a BB requirement and not a global two-handoff budget. It silently discards further directives and can still fan out to more than two total handoffs.

### Cited Findings
- Human messages start depth zero. Each mirrored assistant message has `depth = cause.depth + 1`. After the BB thread finishes, only the final assistant row is scanned for exact whole-line `[[ask ...]]` matches, and only when `cause.depth < 2`. The parser deduplicates target agents and excludes self. There is no surfaced rejection at the depth boundary. — [Human depth](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/store.ts#L307-L350), [agent depth and handoffs](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L185-L261)
- Prompt text says at most two handoffs per originating message, which is broader than the actual per-path check. — [Prompt](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/apps/rooms/src/runtime.ts#L121)

### Inferences
- Single chain: human(0) → Builder reply(1) → Reviewer reply(2) → Builder reply(3), after which Builder's directive is ignored. Multiple human-addressed agents and multiple targets at each level multiply total invocations.
- Replace this hidden chain limit with intentional addressing, receipt/ack and no-post idle semantics, plus visible operational controls. A publish tool alone does not mathematically prevent loops if every post wakes everyone. Routing policy must distinguish targeted requests, ambient messages, replies/results, subscriptions, and self/duplicate events. Explicit operational budgets, if desired, should pause visibly with reasons and resumability, not silently drop a handoff.

### Gaps
- No user-configurable budget or reason code exists in the audited implementation.

## What did Work Together establish, and what was missed?

### Takeaway
The previous 24-line report established an execution-cell/security integration, not a researched peer-chat architecture. It mentioned settlement tools but failed to apply their key lesson: tools make explicit, authenticated public reports while execution proceeds independently. Work Together's public BB fork still does not prove an arbitrary peer-room product, since companion services are separate and were not available in the inspected public repo list.

### Cited Findings
- The previous report explicitly described a BB execution cell for separate MCP/web/worker services and recommended architectural lessons rather than cherry-picking. It did not document a traced chat-post/delivery lifecycle or prove peer-agent participation. — [Original audit](https://github.com/csells/bb/blob/a05bc0eea5ede0ffe2a99cf607c55e1afef43e34/specs/research/work-together.md)
- Upstream PR2324 was a Grok launch-options change accidentally opened against upstream, closed unmerged; author points to downstream PR7, now merged. This is not an upstream BB Rooms feature PR. — [PR2324](https://github.com/get-bb/bb/pull/2324), [author correction](https://github.com/get-bb/bb/pull/2324#issuecomment-5389393496), [PR7](https://github.com/timmoshu/bb/pull/7)
- Work Together main is still `0f53aacbec1a46680e6aa392408ad7f8d1333c87` at inspection. Its release runbook specifically excludes deploying separate WT MCP/web/worker services. — [Runbook](https://github.com/timmoshu/bb/blob/0f53aacbec1a46680e6aa392408ad7f8d1333c87/docs/bb-candidate-cell-release.md#L1-L10)
- Explicit tools `wt_checkpoint_report`, `wt_result_report`, and `wt_needs_you_report` accept strict report schemas/idempotency keys, with no actor/goal/workspace/thread fields supplied by the agent. Tool handler injects trusted `bbThreadId` and server-held cell bearer. Result reporting explicitly does not finish Work; needs-you instructs call once and stop. These are work-state reports, not evidence of arbitrary public chat publishing. — [Tool contracts](https://github.com/timmoshu/bb/blob/0f53aacbec1a46680e6aa392408ad7f8d1333c87/apps/server/src/services/work-together-settlement-tools.ts#L7-L160), [trusted injection](https://github.com/timmoshu/bb/blob/0f53aacbec1a46680e6aa392408ad7f8d1333c87/apps/server/src/services/work-together-settlement-tools.ts#L170-L238)
- Repository-deliver additionally uses project/thread context and a default idempotency key derived from thread and turn. Do not confuse this with chat publication. — [Delivery](https://github.com/timmoshu/bb/blob/0f53aacbec1a46680e6aa392408ad7f8d1333c87/apps/server/src/services/work-together-settlement-tools.ts#L258-L282)
- Adapter branch pinned `848ad9550784c5ff22ea962aa5d757c3f1d91084` exposes binding-scoped bootstrap/commands/events/subscribe and a stream target choosing primary thread or child attachment. It is not itself a social message bus for equal agents. — [Port](https://github.com/timmoshu/bb/blob/848ad9550784c5ff22ea962aa5d757c3f1d91084/apps/server/src/room-distribution/room-distribution-port.ts#L10-L58)
- Adapter has exact-turn steer/interrupt commands and queue-if-active ordinary sends. Actor stamps derive from authenticated principal; request identity replay/conflict handling precedes dispatch. `branch.publish` invokes repository branch publishing, not a room-post tool. — [Commands](https://github.com/timmoshu/bb/blob/848ad9550784c5ff22ea962aa5d757c3f1d91084/apps/server/src/room-distribution/binding-backed-room-commands.ts#L64-L108), [dispatch](https://github.com/timmoshu/bb/blob/848ad9550784c5ff22ea962aa5d757c3f1d91084/apps/server/src/room-distribution/binding-backed-room-commands.ts#L730-L819)
- BB multiplayer PR799 is closed, unmerged (Aug7), and explicitly uses claimed identities, not authorization by identity. Its author described a backup draft not prepared for merge. — [PR799](https://github.com/get-bb/bb/pull/799)

### Inferences
- What our code retained: independent execution threads, room-level membership checks, persistent room records. What it ignored: explicit report tools, separation of private execution and public report, trusted activation identity, exact-turn steering, structured admission/replay receipts. The current implementation is independently authored, not a faithful Work Together chat port.
- Work Together is a useful source for security and execution admission. Buzz/Gas City are needed to establish room participation and wake/idle semantics; do not invent unavailable WT companion behavior.

### Gaps
- Companion Work Together MCP/web/worker source was not found among publicly listed timmoshu repositories. No claim is made about its scheduler, agent post command, or whether all its final text is private.
- Did not run Work Together tests or its deployment. Claims here are source inspection.

## Can BB support a proper implementation?

### Takeaway
Yes: existing BB private threads, native dynamic tools, send/steer/stop, and provider tool bridges supply the execution substrate. Rooms must supply authenticated social identities, explicit publication, durable inboxes/receipts, scheduling policy, and public streaming lifecycle. This is substantive integration work rather than a prompt correction.

### Cited Findings
- `bb.agents.registerTool` registers schema-validated native tools; `configure` selects tools/instructions per thread/session. Changes apply on next session construction, not live hot-mutation. — [Plugin SDK](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/packages/plugin-sdk/src/backend-contract.ts#L1615-L1668)
- Native tool context includes trusted threadId/projectId/AbortSignal, but **no turnId/runId**. Configuration metadata is explicitly writable by the agent/API and untrusted. — [Context](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/packages/plugin-sdk/src/backend-contract.ts#L1068-L1082), [metadata warning](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/packages/plugin-sdk/src/backend-contract.ts#L1141-L1155)
- Pi's bridge actually calls `pi.registerTool`, forwards tool-name/arguments over its protocol, and handles cancellation. — [Pi extension](https://github.com/get-bb/bb/blob/9a47d42c78ca9689af0b78da9b3155a8c0b36251/plugins/provider-pi/src/bridge/bb-pi-extension.ts#L311-L343)

### Inferences
- Prefer a Rooms plugin exposing room.read, room.ack, room.post, room.request, room.stream.begin/append/commit/abort, room.yield. Identity is resolved server-side from a trusted thread→agent binding plus immutable activation lease; never accept author identity in model arguments. CLI/MCP wrappers can target the same validated protocol with narrowly scoped credentials.
- BB's current native context can establish agent identity but not an immutable turn fence alone. Add trusted turnId to tool context or validate a broker-issued activation capability with server-held binding and revocation. Do not use mutable plugin metadata as authentication.
- Keep public room log and private execution log separate. Provider text/status/tools belong in an optional activity inspector. Only explicit successful public-post/stream calls create public messages. Stream chunks own one message, monotonically ordered/idempotent and abortable; no parsing arbitrary assistant prose.
- Independently addressable participants share a room membership model; humans and agents differ in authentication/execution capabilities, not social parent-child status. Membership roles and authority to run privileged tools are separate policies.
- Durable event IDs, per-agent delivery cursors, activation leases, atomic publish/outbox, immutable replyTo/turn routing, queue receipts, retry idempotency, and visible hold/revocation should survive process restart. Idle without public output is a valid successful activation.
- Acceptance: two humans plus two independent real agents; each posts only through its credential/tool; forged author rejected; raw final containing multiple voices/mentions creates zero public messages; targeted peer receives exactly once; ambient message need not wake; two agents can choose silence; busy input has correct receipt and later incorporation; public stream updates/reconnect/abort do not duplicate/wake per token; restart/retry/stop/revocation fences stale publishers; beyond-two exchanges work without hidden truncation; explicit human hold can stop the room.

### Gaps
- The specific native-tool integration, turn-fence design, and model compliance require spikes. Source support alone does not establish end-to-end implementation correctness. Pi is the currently available authenticated provider; other providers must be verified separately.
