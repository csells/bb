# Buzz: explicit participation by independent humans and agents

## What actually makes Buzz a multi-participant conversation?

### Takeaway

Buzz separates the agent's private execution from the public conversation. Incoming room events wake an independently authenticated agent; that agent must explicitly invoke a messaging CLI/tool to publish as itself. Provider completion is not a public message. Its instructions make doing nothing a valid outcome when there is nothing useful to add, and its code suppresses self-authored events.

### Cited Findings

- Audit scope: read-only code at `block/buzz` commit `836e7d0d06789765b4d98a93c2b509a2a0fbd1bf` (existing `/tmp/buzz-audit-src`) and `block/buzz-app` commit `02c01c17c18521b37c3615e9dbd7a319e1784218` (`/tmp/buzz-app-parity-audit`). GitHub current-head lookup on October 9 returned newer heads `16eb0b6685a9ea5cd06275aed172903dac69f225` and `6bdf9e4155ddabc773226e4b9ccd03bf87553f79`; this is a pinned implementation audit, not a claim to have read every subsequent change. [Buzz audited tree](https://github.com/block/buzz/tree/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf), [Buzz-app audited tree](https://github.com/block/buzz-app/tree/02c01c17c18521b37c3615e9dbd7a319e1784218).
- The harness documentation draws the exact relay WebSocket → `buzz-acp` → ACP stdio agent → Buzz CLI → relay path. Each named agent should have its own Nostr keypair and relay membership. This is cryptographic identity, not attribution inferred from generated prose. [README architecture and identity](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/README.md#L7-L47).
- System instructions identify `buzz` as the primary interface; auth comes from `BUZZ_RELAY_URL`, `BUZZ_PRIVATE_KEY`, and optional `BUZZ_AUTH_TAG`. Commands produce structured JSON and classify network/auth/conflict failures. [base_prompt.md](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/base_prompt.md#L8-L18).
- Canonical publication is `buzz messages send --channel UUID --reply-to EVENT_ID --mention RECIPIENT_PUBKEY --content -` with the chosen public text on stdin. `--mention` can repeat. The CLI resolves recipients separately from visible names, rejects nonmember recipients, constructs a kind-9 event with thread metadata, signs, submits, and returns the actual signed `mention_pubkeys`. [messages.rs input and member validation](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-cli/src/commands/messages.rs#L601-L648), [thread, event, sign and submit](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-cli/src/commands/messages.rs#L673-L757).
- CLI signing uses the client's own key and injects the configured auth delegation tag exactly once; arbitrary auth tags supplied by a caller are rejected. The relay independently verifies the signed event before ingest. [client.rs](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-cli/src/client.rs#L580-L607), [relay verification](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-relay/src/handlers/ingest.rs#L2401-L2419).
- Explicit publication and silence are written into the conversational contract: publish useful requested results via CLI; answer humans; otherwise silence is usually correct; never post empty acknowledgment or announce one's silence. Mentions should request action rather than merely name a teammate. Completed delegation results mention the delegator; acknowledgment does not. These are behavioral instructions rather than a mathematical loop bound. [mention and callback rules](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/base_prompt.md#L43-L54), [publication and silence](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/base_prompt.md#L68-L80).
- The harness also enforces self-suppression in code: `ignore_self` drops a relay event whose author key equals the agent key before further dispatch. `ignore_self` is enabled unless explicitly disabled. [lib.rs](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/lib.rs#L3563-L3566), [config.rs](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/config.rs#L1179-L1182).
- Ordinary ACP message chunks are logged as execution activity; thought chunks are separately logged. The local-task contract explicitly says the harness does not automatically post final text. Public message creation is the CLI path above. [session update handling](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/acp.rs#L1828-L1871), [task contract](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/session_model_task.md#L1-L11).
- Humans and agent senders use the same relay message model. Buzz-app validates explicit kind-9 mention recipient keys and channel membership, including fresh checks before dispatch rather than trusting an old cached roster. [session.ts](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/src/features/relay/session.ts#L974-L1025).
- ACP runtime workers and public participants are different concepts: `--agents N` is a worker pool under one bot key; N workers do not become N named room identities. Session policy defaults to channel, with independent thread scope available; DMs remain one conversation. An agent's multiple sessions share workspace and durable memory but not provider context or in-progress reasoning. [README shared identity](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/README.md#L215), [channel-session contract](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/session_model_channel.md#L1-L5), [thread-session contract](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/session_model_thread.md#L1-L5).

### Inferences

- Reuse the separation of `Participant`, `AgentRuntime`, `ProviderSession`, `PublicMessage`, `Delivery`, and `ActivityEvent`. Each public agent needs a stable distinct principal and independently scoped publication credentials. A provider transcript cannot be the room's authoritative message log.
- A model may still generate text pretending to quote another participant. Identity-bound publication prevents that prose from becoming an actual second participant's message. It does not prevent misleading prose; explicit instructions and UI attribution still matter.
- The BB Rooms prototype's `[[ask ...]]` parsing and automatic public mirroring should be replaced by an authenticated command/tool. Do not parse generated prose for author changes or use a regex as the message bus.
- Tools enable natural silence but do not guarantee agents never deliberately ping-pong. Retain visible user-controlled activity budgets, rate controls, admission policy and stop; do not impose an undisclosed universal two-hop conversation limit.

### Gaps

- This audit has not run Buzz or its test suite, copied credentials, called models, or changed Buzz staging. Code conclusions must not be represented as new live acceptance results.
- No claim is made that the whole Buzz relay security model or every harness adapter is flawless. The inspected boundary is identity-bound message construction, explicit submission, and provider-output separation.

## How does delivery, concurrency, steering and recovery work?

### Takeaway

Buzz has an event-routing and scheduling subsystem around the model: admission, per-scope queues, persistent provider sessions, explicit busy-input policy, and acknowledgments for steering. Correctness requires more than calling two models concurrently. Its recovery mechanisms are substantial but bounded; they should not be described as exactly-once end-to-end execution.

### Cited Findings

- The configurable inbound author gate supports owner-only (default), allowlist, anyone, and nobody; owner commands bypass ordinary author filtering. Distinct humans and other agents must actually be admitted, not just present as member names in the UI. [README author gate and controls](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/README.md#L134-L187).
- Subscription rules can filter channel IDs, event kinds, author/content and require a `p` tag matching the intended agent. Default subscription is mentions. [filter.rs rule type](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/filter.rs#L75-L113), [configuration](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/config.rs#L335-L356).
- `EventQueue` tracks queues, in-flight scopes, retry counts/deadlines, cancelled batches and withheld native-steer events. It enforces bounded pending queues. `DedupMode::Drop` intentionally discards new work while a scope is active; the app config chooses `queue`, so this lossy mode is not an appropriate assumed default for our room. [queue state/push](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/queue.rs#L368-L460), [app runtime configuration](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/crates/agent-controller/src/runtime.rs#L186-L215).
- Dispatch drains bounded batches, sorts replayed events into timestamp order, marks a scope in flight, and preserves cancelled work when merging into a new turn. This is scope-based concurrency rather than one global room turn. [queue.rs dispatch](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/queue.rs#L585-L627).
- Busy-input modes are steer, queue, interrupt and owner-interrupt. The default is steer. Channel policy is default; thread policy supports distinct sessions within a channel. [config.rs](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/config.rs#L358-L383).
- Actual steering is capability-sensitive. Goose uses a run-ID-targeted method; an adapter advertising `_meta.steering.supported` uses `_session/steering`; unsupported adapters fall back to cancellation plus a merged prompt. A generic JSON-RPC success is insufficient: known acknowledgment outcomes must confirm delivery, because some adapters return `{}` to unknown methods. [transport selection](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/acp.rs#L1490-L1560), [ack validation](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/acp.rs#L1670-L1728).
- Authenticated owner `!cancel` is scoped to the targeted channel/thread rather than canceling unrelated work; `!shutdown` shuts the harness down. They require an exact command body plus a separate mention tag, not a model interpretation of a stop request. [owner command processing](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/lib.rs#L3568-L3619).
- Membership removal drains queued events and invalidates channel sessions, while already running work can complete and its later writes may be rejected by the relay. This is a documented boundary, not instantaneous revocation of all computation. [membership cleanup](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/lib.rs#L3515-L3556).
- CLI network retries retain identical signed event bytes and generate fresh request-auth proofs. After ambiguous failure exhaustion, `DeliveryUnknown` stops callers from re-signing a potentially accepted write. The relay treats an already inserted event as accepted duplicate and returns before subsequent side effects. [stored-event retry](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-cli/src/client.rs#L1120-L1172), [ingest deduplication](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-relay/src/handlers/ingest.rs#L3421-L3463).
- Relay replay uses remembered timestamps and a two-generation bounded event-ID dedup set. Old IDs can age out; replay protection is not unlimited durable dedup. Replay starts at the earlier of last-seen and known dropped-work timestamp, so queue pressure can be recovered within available history. [bounded dedup](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/relay.rs#L1094-L1103), [replay cursor](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/relay.rs#L1261-L1298). The README expressly says queue-overflow recovery does not guarantee complete delivery. [recovery limits](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/README.md#L298-L315).
- Inspected source tests include steer queue-to-prompt behavior, cross-thread reply targeting, preserved requeue events, native-steer expiry recovery/FIFO, and relay dedup behavior. These were read, not executed. [queue steering tests](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/queue.rs#L3221-L3430), [steer recovery tests](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/queue.rs#L6279-L6453), [relay dedup tests](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/relay.rs#L5172-L5308).

### Inferences

- Reuse independent per-agent/per-room sessions and serialized processing within a session. Two agents can work at once; two humans can both submit messages without assuming a single privileged prompt author. Persist message acceptance before scheduling.
- Record delivery states and cursor/ack data in our own durable store; avoid treating a provider transport acknowledgment as evidence that an explicit public message was accepted. Public command idempotency keys should survive worker restarts.
- Preserve new inputs while a model is busy; expose queued versus steered truthfully. A model tool call may delay immediate steer processing, so acceptance and execution visibility must be separate.
- Keep message publication metadata structured: sender derived from auth, room, message ID, causation, thread/reply ID, explicit recipient IDs, idempotency key. Avoid automatic mentions derived from arbitrary narrative; selected recipients should be authoritative.

### Gaps

- Full restart-persistent inbox guarantees were not established for every Buzz queue path. Its in-process queue and bounded replay should not be reused unchanged if our product promises a durable inbox.
- Source tests do not prove correct behavior of our BB provider integration. We need real-provider spikes for no-publication, separate principals, interruption and incoming-message handling before implementation decisions are considered validated.

## What should BB Rooms reuse, and what must be proved in spikes?

### Takeaway

Reuse Buzz's explicit publication and independent identity model, not its current personal browser broker or a raw transcript mirror. Visible streaming should be a selected public-message operation, while provider execution/activity stays a separate stream with separate audience permissions.

### Cited Findings

- Buzz's observer captures raw ACP activity as a process-local stream. When relayed, it encrypts the payload to the owner, signs an observer frame, and publishes it separately from ordinary room messages. This includes text/tool/thought activity; it is not consent to show all that data to every room member. [observer bus](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/observer.rs#L1-L5), [owner encryption/publication](https://github.com/block/buzz/blob/836e7d0d06789765b4d98a93c2b509a2a0fbd1bf/crates/buzz-acp/src/lib.rs#L1791-L1830).
- Buzz-app actually consumes incremental observer events via browser transport. Its shared activity renderer accumulates agent message/thought chunks and tool changes. [browser live transport](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/src/features/relay/broker-live.ts#L94), [activity rendering](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/src/features/agents/activity-transcript.ts#L431-L450).
- Browser hosting is currently personal: the broker loads one identity key on startup and derives one viewer. The ordinary publication route signs with that closure key. Independent humans behind one unchanged broker URL therefore share its identity. [key and viewer](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/browser-host/relay-broker.mjs#L698-L716), [signing route](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/browser-host/relay-broker.mjs#L2541-L2548).
- Browser mode supports relay messaging but native local agent-control operations are absent. The app runtime's actual launched agent defaults include distinct injected key, mentions, queue dedup, steer, and observer enablement. [browser control absence](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/src/features/agents/control.ts#L417-L431), [runtime wiring](https://github.com/block/buzz-app/blob/02c01c17c18521b37c3615e9dbd7a319e1784218/crates/agent-controller/src/runtime.rs#L186-L215).
- Prior local context was read via `bb thread log` for commonly-gascity and Buzz staging. The former records a bridge that originally posted complete Gas City replies and later added incremental mirror updates; the latter records that Buzz's public conversation used completed CLI posts, with owner activity streamed in a separate panel. Those are historical thread reports rather than tests rerun in this audit. Commonly context: @thread:thr_t2uu3y2mi4. Buzz context: @thread:thr_9phapywpk3. The earlier source audit separately documents the browser identity and hosting limitations. [Local browser audit](/Users/csells/.bb/plugins/environment-personal-workspace/host-data/workspaces/thr_hgth8j3mzz/specs/research/buzz-browser-parity.md).

### Inferences

**Recommended architecture decisions:**

1. Reuse explicit CLI/MCP publication, scoped per-agent credentials, structured recipient IDs, self-suppression, independent sessions, queued busy input, acknowledged steering, and a separate private activity channel.
2. Do not reuse the personal browser broker as multi-human authentication. Use per-human login/session identity and per-agent service principals; room membership must be checked independently for every participant's reads and writes.
3. Do not auto-publish assistant final text or commentary. A selected public stream should begin through an explicit `message.begin` operation and accept append/replace chunks under the same principal, message ID, and sequence. `message.commit` creates the actionable event; interim chunks update UI only and do not repeatedly wake recipients. A simpler first stage is explicit complete CLI posts plus visible queued/working/tool status, but this does not satisfy public response streaming.
4. Do not equate possession of a process with permission to speak as any participant. The server derives sender identity from credential capability; an `authorId` in JSON cannot override it. Agent workspaces should not expose other agents' credentials.
5. Make run-loop controls visible and configurable. Distinguish room-wide pause, cancel this agent/run, revoke participant, policy admission, maximum concurrent runtime work, resource budgets and circuit breaker. None is the same as a universal two-handoff cap.

**Necessary isolated spikes (proposed, not executed by this researcher):**

- **Publication boundary and attribution:** start two independent provider sessions A/B with distinct scoped room CLI tokens in separate workspaces; A emits private prose containing fake A/B transcript but does not invoke the tool. Assert zero public agent messages. Then A invokes CLI send to B; assert exactly one stored sender A and B's independent wake. B publishes with its own CLI token; assert actual sender B. Forged body sender and cross-agent stream append must fail.
- **Silence and loop control:** provide an agent-to-agent informational message with no new request; allow provider to finish without publication; assert delivery completed with zero public messages and no recursive wake. Then request a finite collaboration exceeding two transfers; verify no hidden hop cap truncates it and that only explicit mentions wake participants. Deliberately induced endless mentions must be stopped by the disclosed budget/cancel mechanism, not by mirroring completion.
- **Busy input with two humans:** while A performs a real bounded tool action, human H2 posts a new request after H1. Assert both messages accepted with original authors; second input durably queued or acknowledged steered, never silently lost; B can work concurrently. Cancel A; B continues. Verify eventual delivery and no duplicate execution on rejected steering.
- **Selected public stream:** explicit begin returns message ID; stream at least three visible increments before commit; private provider chunks and tool output remain absent from room; recipients wake once after commit; owner activity can still show live tool status. Reconnect a second human browser midstream and recover same message, without duplicate message or duplicate wake.
- **Provider streaming adapter:** distinguish a scripted CLI that appends three prepared chunks from actual incremental model output. The former proves message protocol only. The harness needs an explicit public destination/tool choice before forwarding selected incremental text; streaming tool-argument deltas may be an adapter option, while repeated append tool calls add round trips. Never fall back to mirroring all assistant output when this adapter is missing.
- **Failure/retry:** drop publication acknowledgment after durable commit; retry same command idempotency key and verify one message and one recipient delivery; restart worker between public commit and inbox ack; reconnect browser and relay; verify event cursor behavior. Late append after cancellation/revocation must be rejected.
- **Reality check:** repeat core protocol spike with an actual intended production model/harness, not only mocked adapters or an easy small-model happy path. Record provider session IDs, accepted delivery IDs, CLI receipts and public messages; inspect absence of unpublished transcript content. Existing demo assertions that two reply bubbles appeared are insufficient.

### Gaps

- No native selected-public-message streaming operation was established in the inspected Buzz CLI send path. The positive streaming claim supported here is owner activity streaming; our selected stream proposal requires a new protocol and explicit test.
- This researcher did not execute runtime spikes; parent was notified with exact tool/auth mechanics and proposed invariants. All candidate runtime spikes must run in separate scratch/data inside the disposable Rooms VM. Stable BB, Buzz VM and user Workshop data remain untouched.
