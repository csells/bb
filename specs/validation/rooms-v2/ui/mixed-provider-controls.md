# Mixed-provider controls regression

The final candidate's compiled/minified UI passed the expanded fixture in Chromium and Playwright WebKit inside the disposable VM. Both final runs passed twelve assertion groups with no JavaScript errors. [Final Chromium log](budget-fixed-ui-chromium/test.log), [final WebKit log](budget-fixed-ui-webkit/test.log), [final client/server hashes](budget-fixed-client-sha256.txt), and [Turbo build/typecheck/26-test log](budget-fix-build.log) identify the evidence. The earlier ten- and eleven-group checkpoints remain in the `mixed-ui-*` and `final-mixed-ui-*` paths.

The mixed-provider browser flow exposed a real budget-edit race. The settings form was keyed by the server's budget, so an incoming snapshot remounted it and overwrote an unsaved blank/unlimited edit. The [focused red result](budget-ui-red/test.log) reproduces this deterministically: the displayed persisted budget changes to1 while the input's blank draft is overwritten with1. The fix keeps a controlled draft initialized when opening Room controls. The final fixture waits until the new persisted budget is rendered, verifies the blank draft remains intact, and checks the browser sends `maxActivations:null`. Both prior mixed runs passed nine conversation groups before this issue; the first was initially diagnosed too narrowly as harness timing. Retained evidence in `mixed-public-participation-attempt1` and `mixed-public-participation-attempt2` records the corrected diagnosis.

A second concrete regression involved an uncertain activation with a newer queued follow-up: the previous client labeled the agent Queued and omitted the uncertainty card. The [retained red result](uncertain-ui-red/test.log) reproduces the misleading status after reload. The final fixture verifies Needs attention takes precedence, retained delivery error and owner recovery guidance remain visible, the uncertain card has no working pulse or elapsed indicator, the accepted follow-up remains queued, and human composition stays available.

The permission test first failed against the previous client: Allow once submitted `grantedPermissions:null` even though a Codex permission-grant interaction required the requested profile. The [retained red result](permission-ui-red/test.log) captures that mismatch. The revised client parses the shared interaction payload schema, sends the requested network/filesystem profile, renders only provider-offered decisions, and supports the offered session grant. The green fixture intercepts and checks the actual browser submissions for an allow-once grant, deny-only request, and session-scoped command grant.

The steering fixture reloads working Codex, Claude Code and Pi snapshots separately, clicks each real Steer now control, and checks the submitted text and honest sent/queued receipt copy. These synthetic API interactions verify presentation and HTTP payload construction. Actual native-provider steering and model-observed effects have separate runtime evidence; this fixture does not replace it.

The same runs retain pre-output pending indicators, elapsed time, writable composer, temporary status failure and recovery, stream/pending coexistence, terminal clearing, reload, 16px touch input sizing, shared drawer usability and app-root behavior. No provider/model call occurred during either fixture run.

A preceding static-server setup used `dist/client` instead of the actual `dist/web` output and received HTTP404 before a browser launched. Its server log is retained as `mixed-ui-static-wrong-root.log`; it is not an application failure or a passed check. The corrected static server was stopped after verification.
